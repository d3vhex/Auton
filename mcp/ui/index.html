Manual repair

Queues a repair task for the workers. They still check the auton-apps allowlist, the resource lock, the cooldown and the hourly budget, and every kubectl call is audit-gated. Image, config, scheduling and PVC problems stay report-only.

A repair plan that the policy engine rated above the automatic tier waits here. Nothing in the cluster changes until somebody approves it; rejecting sends the incident back to a human.

Learned profiles

Every verified repair writes an outcome, and the outcomes change how the next repair of the same resource is done. Learning may only make the platform more cautious or tune a bounded number: a bigger OOM bump, a higher tier (a human has to approve), a longer cooldown, a smaller per-resource budget, or a quarantine. It never widens permissions, never lowers a tier and never changes the action — and every adaptation is written to the audit log before it is applied.

Model provider

Switching to a remote provider disables the local model completely — there is no fallback. local-only refuses remote providers, and a remote provider without a key is rejected. The key is never returned by the API; changes are written to the auton-model-config ConfigMap and the auton-model Secret and audited without the key value. 

—

API access token

The page you are looking at contains no data and is served without a token. Everything that does something — running a task, reading incidents or audit records, changing provider settings — goes through an API that can execute shell commands and patch workloads in your cluster. That is why it requires a bearer token.

Where do I get it?

kubectl -n auton get secret auton-api-token -o jsonpath='{.data.token}' | base64 -d

or run ./scripts/install.sh --show-token.

Where is it stored?

Only in this browser's localStorage. It is never embedded in the page and is sent only to this origin (no third-party requests). Use “Forget token” to remove it.
